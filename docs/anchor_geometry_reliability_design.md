# Anchor Geometry Reliability Design
Date: 2026-03-02
Status: Proposed

This document captures an earlier anchor-geometry investigation. The current
ranking implementation lives in `src/data/guess_candidate_data.rs` and
`src/logic/redaction_guessing_component/helpers/guessing.rs`.

## 1. Introduction
### 1.1 Service description
This service tries to recover words that were hidden under black redaction boxes in PDF files.

At a high level, it does three things:
- finds where redactions exist in a document,
- studies nearby visible text to understand what might fit in each hidden spot,
- returns an ordered list of guesses for each redaction.

The service is designed for repeatable, evidence-driven improvement. That means we do not treat guesses as purely subjective. We measure quality with fixed benchmarks and track whether changes make results better or worse.

### 1.2 Important service details
The service is evaluated against two kinds of quality goals:
- known real redactions that we can score directly,
- synthetic redactions used to check that we are not overfitting to only a few known examples.

It also enforces deterministic behavior:
- if the same file is processed twice with the same settings, the output should be the same.

This matters because the project goal is not only to improve average quality, but to build confidence that improvements are real, stable, and explainable.

### 1.3 Problem description
The main issue is reliability in how the service lines up visible text around a redaction.

In plain terms, the service uses nearby words as reference points to estimate what length and position a hidden name or phrase should have. In some cases, that reference-point choice is inconsistent. When that happens, ranking quality can drop even if the nearby words look more informative.

A second issue is explainability. We can sometimes see that a result got worse, but we cannot always fully explain every internal decision path from the output artifacts alone. That slows down evidence-based improvement.

### 1.4 Requirements governing the problem
- Accuracy target: top-1 on canonical known redactions.
- Fallback objective: smallest K where recall@K = 1.0.
- Determinism: same input + config + code must produce identical outputs.
- Anti-overfitting: evaluate synthetic redactions across all PDFs in `test_data/`.
- No-regression policy against locked baselines.
- Evidence-first policy for algorithm behavior changes.
- Performance can remain soft-gated until recall reaches acceptable margin (>= 0.8), then becomes hard-gated.

### 2.2 Underlying-text context workflow (redaction-side geometry)

- context span meta key: `src/data/redaction_scan_data.rs:23` (`context_spans_json_v1`)

Underlying text geometry is generated by text parser logic that applies coarse width estimation:
- extraction entry: `src/dependency/pdf_redaction/text_parser.rs:9` (`extract_page_text_runs`)
- width approximation: `src/dependency/pdf_redaction/text_parser.rs:177`

That approximation is:
- width = `font_size * 0.6 * char_count`

This stream is useful for context discovery and anchoring hints, but its geometry fidelity is lower than run-level metrics and shaping data.

### 2.3 Font-run workflow (run-side geometry)

This stream provides higher-fidelity geometry than underlying context hits and is the best candidate for primary anchor coordinate selection when available.

3. Attempt anchor selection.
   - `select_anchor_pair`: `src/logic/redaction_guessing_component/guess_logic.rs:1807`

Current anchor decision visual:
```text
context hints + row runs
  -> try same-run two-sided
  -> else try pair-based two-sided
  -> else recover one-sided
  -> resolve anchor text/x per side
       - may use run-derived x
       - may use hint_x in hint-superset branch
```

The key unstable behavior is in text-superset branch handling:
- when `hint_text.contains(run_text)` is true, the resolver can return `hint_x`.

### 2.5 Candidate scoring and ranking workflow
Candidate ranking currently keeps two error concepts:
- `effective_error_pt` used for ordering.
- `raw_error_pt` serialized into candidate `error_pt`.

Evidence:
- sorting by effective error: `src/logic/redaction_guessing_component/guess_logic.rs:1444`
- score from effective error: `src/logic/redaction_guessing_component/guess_logic.rs:1477`
- output `error_pt` from raw error: `src/logic/redaction_guessing_component/guess_logic.rs:1478`

This behavior is internally coherent, but when anchor geometry source changes unexpectedly, ranking can shift even when text cues seem stronger.

### 2.7 Summary of current-state limitations
- The system has two geometry-bearing text paths with different fidelity and different reconstruction assumptions.
- Anchor x-source selection is not consistently explicit or constrained by a canonical reliability contract.
- Some regressions can be measured but not fully explained from machine-readable diagnostics alone.

## 3. Solution
### 3.1 Recommended solution overview
The recommended solution is to make anchor geometry a canonical, deterministic service behavior, not an emergent result of competing heuristics.

The service should keep both extraction streams, but it must produce one authoritative anchor geometry decision per row with explicit source semantics and full rejection traceability.

### 3.2 Solution architecture and workflow
Solution architecture visual:
```text
Dependency layer (raw signals)
  - pdf_redaction text/context extraction
  - pdf_font_run extraction
        |
        v
Data layer (canonical geometry normalization)
  - align context hints to run geometry
  - produce canonical anchor candidates
  - assign source labels and source deltas
  - preserve alternative candidates + rejection metadata
        |
        v
Logic layer (deterministic anchor resolver + ranking)
  - select final anchor mode and coordinates deterministically
  - rank candidates using canonical geometry decisions
  - emit stable row-level trace artifacts
```

Solution workflow:
1. Ingest both raw signal streams exactly as today.
2. Normalize to canonical anchor candidates with explicit source-quality metadata.
3. Apply deterministic source precedence and fallback semantics.
4. Emit final anchor selection plus rejected alternative reasons.
5. Rank and report using canonical geometry decision artifacts.

### 3.3 Anchor geometry source model
For every selected anchor x-coordinate, the system should always emit:
- selected source label,
- selected coordinate,
- alternate coordinate when available,
- selected-versus-alternate delta.

Stable source taxonomy:
- `run_exact`
- `run_prefix_projection`
- `hint_only_fallback`

Required behavior:
- If run mapping is valid, run-derived geometry is preferred.
- Hint-derived geometry is reserved for explicit fallback when run mapping is unavailable or invalid.
- Text expansion can occur, but source selection must remain explicit and deterministic.

Why this resolves the measured issue:
- The `EFTA00101126` regression came from geometry shift, not missing phrase context.
- Explicit run-first semantics prevent silent hint-x substitution when run geometry exists.

### 3.4 Anchor decision explainability model
For every row, the service should emit a machine-readable decision record containing:
- selected anchor mode (`two_sided`, `left_only`, `right_only`),
- selected left/right anchor text,
- selected left/right anchor coordinates,
- selected coordinate source labels,
- reason codes for rejected alternatives,
- reason code for fallback selection when fallback occurs.

Reason-code expectations:
- stable across runs,
- machine-parseable,
- complete enough to explain mode flips and source changes.

Why this resolves the measured issue:
- The `ADRIANA` row-13 transition is currently visible but not fully explainable.
- Complete reason-code coverage turns mode flips from opaque outcomes into verifiable decisions.

### 3.5 Ranking and diagnostics behavior in solution state
Ranking behavior remains anchored in current scoring semantics:
- ordering by effective error remains valid,
- raw error remains available,
- but both are interpreted in the context of explicit canonical geometry decisions.

Diagnostics behavior in solution state:
- row-level decision traces become first-class outputs,
- traces are deterministic and diffable,
- ranking changes can be attributed directly to geometry decision changes.

### 3.6 Service-level quality behavior in solution state
Known-target quality behavior:
- top-1 remains the target objective,
- if top-1 is not feasible, reported best-feasible-K is minimized and non-regressed unless explicitly approved.

Determinism behavior:
- repeated identical runs produce identical guesses and identical row-level trace artifacts.

Overfitting behavior:
- fixed-seed synthetic tier remains binding pass/fail,
- exploratory seed tier remains diagnostic and separately reported,
- coverage remains all PDFs in `test_data/`.

Evidence behavior:
- algorithm behavior changes are accepted only with measurable, disconfirmable evidence versus locked baseline artifacts.

### 3.7 Why this solution addresses the problem
This solution directly addresses each measured failure mechanism:
- It removes silent coordinate-source ambiguity in anchor resolution.
- It preserves useful context text expansion while constraining geometry source semantics.
- It provides full explanation of mode/source transitions through stable reason codes.
- It keeps architecture ownership clean and consistent with layer doctrine.
- It strengthens evidence quality by making row-level reasoning auditable and deterministic.

The net effect is a system where ranking changes are attributable, reproducible, and governed by explicit geometry decisions instead of mixed implicit heuristics.

## 4. Baseline and Gate Governance
### 4.1 Required command matrix
Required validation commands (default args):
- `cargo test`
- `cargo run --bin guess_accuracy_benchmark --release`
- `cargo run --bin synthetic_overfitting_benchmark --release`

Expected primary artifacts:
- `benchmark/guess_accuracy.json`
- `benchmark/guess_accuracy.baseline.json`
- `benchmark/synthetic_overfitting_evaluation.json`
- `benchmark/synthetic_overfitting_evaluation.baseline.json`

### 4.2 Hard gate policy
- Hard pass requires:
  - all tests pass,
  - benchmark commands complete without runtime failure,
  - no out-of-band regression beyond margin bands,
  - for `improve` intent bundles, at least one core accuracy metric improves beyond margin.
- Margin policy: `1%` relative margin on hard thresholds.
- Core known-target metrics: `recall_at_1`, `recall_at_5`, `recall_at_20`, `mrr`, `mean_rank_found` (lower is better).
- Synthetic multi-seed panel is binding with `N>=20`.
  - tolerance defaults: `r@20 = 0.01`, `mrr = 0.002`,
  - applied with margin band (`* 1.01`).

### 4.3 Baseline lock/update policy
- Baselines are treated as locked reference snapshots between intentional refreshes.
- Baseline refresh is an explicit governance action after a completed evidence-backed change set, not an implicit side effect of every run.
- If a baseline is missing for a required artifact, bootstrap from current output once, then treat it as locked for subsequent runs.

### 4.4 Regression response protocol
- No retry loop is allowed for hard regression failures.
- On out-of-band regression:
  - emit a regression response artifact,
  - mark rollback required,
  - stop execution for the current bundle sequence.
- Regression response artifact records:
  - gate policy,
  - triggering intent,
  - failure reasons,
  - rollback-required state,
  - benchmark artifact paths used in the decision.
